# TermLink Server Web 当前功能审计与产品优化建议

文档版本：1.0
审计日期：2026-08-27
审计对象：当前工作区源码与本机 `termlink-production-acceptance` 实际部署
文档性质：现状盘点、问题判断和产品路线建议，不替代接口协议与安全设计文档

## 1. 结论摘要

当前 TermLink Server Web 已经形成四个能力层，而不再是单一的服务器管理页：

1. 面向未登录访客的产品官网与下载、版本、套餐、安全、状态页面；
2. 面向普通用户的账号、设备、PC、会话元数据、订阅、订单、安全和隐私门户；
3. 面向管理员的运行、安全、账号、商业化、支付和对账控制台；
4. 支撑 Android、Windows Agent 和 Web 的统一 Server API。

技术基础总体可靠：页面采用服务端渲染，JavaScript 很少；身份使用 OIDC；敏感操作具备 CSRF、最近认证、MFA、操作原因、幂等和审计保护；终端正文不进入 Web，符合端到端加密边界。

当前主要问题不是“功能太少”，而是“已实现能力、运行配置和页面展示没有完全对齐”，以及管理后台的信息架构开始失控。最需要先解决的是：

- AppShip 在当前内网 DNS 下被公开版本读取器的 SSRF 防护拒绝，导致下载页、版本页和系统版本页显示不可用；
- 支付页面固定展示支付方式，但当前支付渠道全部未配置、未启用；
- 账号注销源码已实现，但当前部署没有启用身份注销处理器，页面能力开关没有完全跟随后端运行配置；
- 当前服务器镜像使用 `dev / unknown` 构建元数据，系统版本页无法给出可靠 Server 版本；
- `/account`、`/commerce`、`/admin`、`/admin/commerce` 分成四套入口，普通用户和管理员都需要理解内部技术边界；
- 商业化后台单页包含大量表格和表单，更像内部数据库控制面，而不是高效的运营产品。

建议保留“服务端渲染 + 少量渐进增强”的技术方向，不建议为了视觉或交互直接重写成大型 SPA。先统一信息架构、运行能力开关和异步任务体验，收益更高、风险更低。

## 2. 审计口径

本次结论来自以下证据：

- Web 路由与页面：`server/internal/webportal`；
- Server API：`server/internal/api/api.go`；
- 用户门户和管理员查询：`server/internal/store`；
- 商业化与支付：`server/internal/commerce`、`server/internal/payment`；
- 当前 Docker Compose 容器、PostgreSQL 只读统计和公开页面 HTTP 响应；
- 当前公网入口：`https://termlink.kget.cc:8910`。

本文使用四种状态：

| 状态 | 含义 |
| --- | --- |
| 已实现并可用 | 源码、页面或接口已接入，当前部署具备运行条件 |
| 已实现但未启用 | 源码存在，但当前部署缺少配置、渠道或处理器 |
| 已实现但体验不完整 | 主流程可工作，但页面反馈、导航、筛选或异步状态不足 |
| 建议新增 | 当前没有完整产品能力 |

### 3.1 当前下载页不可用的直接原因

当前 `appship.kget.cc` 通过内网 DNS 解析到 `192.168.9.250`。Agent 自动升级目录已支持显式允许该私网地址，但 Web 的 `PublicReleaseSource` 只允许公网 IP，并没有接收相同的精确私网白名单。连接在发起前即被 SSRF 防护拒绝，因此：

- `/downloads` 无法显示正式下载；
- `/releases` 无法显示动态修复内容；
- `/status` 将客户端版本分发标记为不可用；
- 管理员系统版本页无法展示 Android/Windows 当前发布版本。

正确修复方式是给公开版本读取器增加与 Agent 更新目录等价的“域名 + 精确私网 IP + TLS 主机名校验”能力，而不是关闭 SSRF 防护或允许整个内网网段。

## 4. 产品边界

### 4.1 Web 应承担的职责

- 产品介绍、正式版本和可信下载；
- 身份登录、注册和账号安全入口；
- 用户自己的设备、PC、会话元数据和控制策略管理；
- 套餐、权益、兑换、订单、支付与退款状态；
- 数据导出和账号注销；
- 管理员的账号、准入、商业化、安全审计、版本和运行控制面。

### 4.2 Web 明确不应承担的职责

- 不展示或解密终端正文、命令、快照和历史正文；
- 不提供浏览器终端和远程文件管理器；
- 不从 Web 触发 Windows Agent 自动升级；该能力继续只允许 Android 发起；
- 不提供 Docker 任意命令或服务器 Shell；
- 不显示支付 Secret、私钥、Token、对象存储键或渠道原始回调正文；
- 不以浏览器“支付成功”跳转作为履约依据。

这个边界合理，应继续保留。

## 5. 角色与权限

| 角色 | 当前 Web 权限 | 产品评价 |
| --- | --- | --- |
| `USER` | 公开站点、个人中心、用户门户，只能查看和操作自己的资源 | 合理 |
| `AUDITOR` | 可打开管理台并只读查看；部分有界报表导出在 MFA 后可执行 | 基础审计角色已具备 |
| `ADMIN` | 可执行多数运营、订单、邀请码、兑换码、套餐和人工权益操作 | 权限范围偏大，后续应细分 |
| `SUPER_ADMIN` | 账号角色/状态、注册策略、支付渠道配置等高风险操作 | 仍受 MFA、审计和状态机约束，设计正确 |

当前高风险 Web 操作通常同时要求：

- 当前数据库角色与浏览器会话角色均满足权限；
- 同源校验与 CSRF；
- 最近 10 分钟完成身份认证；
- MFA；
- 3 到 500 字符的操作原因；
- 幂等键；
- 成功或拒绝审计。

这套安全基线应作为不可回退项。

## 6. 公开站点功能

| 页面/能力 | 当前功能 | 状态与问题 |
| --- | --- | --- |
| 首页 `/` | 产品定位、终端连接示意、安全边界、自托管介绍、登录/注册入口 | 已实现；品牌方向与 Android/PC 基本一致 |
| 登录 `/login` | OIDC Authorization Code、PKCE、state、nonce、回调和安全会话 Cookie | 已实现并可用 |
| 注册 `/register` | 按 `OPEN`、`INVITE_REQUIRED`、`CLOSED` 展示注册表单；调用注册 Saga | 已实现；当前部署是 OPEN |
| 下载 `/downloads` | 从 AppShip 读取 Android/Windows 稳定包、文件名、大小、最低系统、SHA-256 | 已实现，但当前部署因私网 DNS/SSRF 策略显示不可用 |
| 版本 `/releases` | 从 AppShip 动态读取版本、Build、发布时间和修复内容 | 已实现，但当前不可用 |
| 套餐 `/plans` | 展示已发布 Catalog 的套餐、价格、周期与购买入口 | 已实现；当前只有免费套餐 |
| 安全 `/security` | 展示 E2EE、设备隔离、本地优先和数据可见性边界 | 已实现 |
| 状态 `/status` | Web、身份、实时、支付和客户端分发的公开摘要 | 已实现但信息价值有限；多数状态固定为“未公开” |
| 主题 | 浅色、深色、跟随系统，跨页面保留 | 已实现；支持减少动画偏好 |

### 6.1 公开站点的产品缺口

- 首页没有清晰的“首次使用三步”：注册、安装 PC Agent、安装 Android；
- 下载页当前失败时没有订阅通知、备用可信入口或上次已验证版本；
- 版本页只展示最新稳定版，没有历史版本、兼容范围和已知问题；
- 套餐页缺少功能对比表、FAQ、退款说明和支付渠道可用状态；
- 状态页不是实际聚合健康页，没有事件、维护公告、历史可用性和最后故障；
- 页脚缺少隐私政策、服务条款、联系方式和 ICP/合规信息入口。

## 7. 普通用户 Web 功能

### 7.1 个人中心 `/account`

当前提供：

- 用户名、姓名、邮箱和角色展示；
- 进入订阅与订单门户；
- 管理员进入 Server Console；
- Windows、Android 的连接指引；
- 跳转 Keycloak 管理密码、MFA 和浏览器会话；
- 安全退出当前浏览器会话。

问题是 `/account` 只是入口页，真正的账号管理位于 `/commerce`。普通用户需要理解“个人中心”和“commerce 用户中心”是两套页面，命名不符合用户心智。

### 7.2 用户门户 `/commerce`

| 分区 | 当前功能 | 状态与问题 |
| --- | --- | --- |
| 概览 | 当前权益、设备数、在线 PC、运行会话数、近期安全事件数和快捷入口 | 已实现；缺少引导任务和异常提醒 |
| 设备 | 设备类型、信任、在线、最后活动、登记时间；MFA 后撤销设备 | 已实现；缺少当前设备标记、重命名和筛选 |
| Windows PC | 平台、架构、Agent 版本、远程路由、在线状态；修改单人/接管/协同控制策略 | 已实现；名称过度绑定 Windows，不利于未来 Linux/macOS Agent |
| 会话元数据 | 会话、PC、状态、在线、创建/结束时间；退出会话可删除服务端加密历史 | 已实现；不显示正文是正确边界 |
| 订阅与权益 | 当前权益、Catalog、套餐、兑换码预览/确认核销、核销历史 | 已实现；当前只有免费套餐、没有兑换批次 |
| 订单与支付 | 创建订单、显示支付入口、主动查单、取消未支付订单、订单和退款历史 | 源码已实现；当前支付渠道未配置，页面仍固定展示支付方式 |
| 安全活动 | 当前账号的脱敏安全事件 | 已实现；固定最近 50 条，无筛选和分页 |
| 数据隐私 | 数据导出、下载、账号注销预检、二次确认、冷静期与取消 | 数据导出可用；账号注销当前部署未启用完整处理器 |

### 7.3 用户门户交互缺口

- 列表统一截取最多 50 条，但普通用户没有“下一页”或完整历史；
- 支付、数据导出、注销、对账等异步任务依靠用户手动点击刷新或查单；
- 高风险操作把“原因输入框”直接放进表格行，移动端密度高；
- 缺少统一通知中心，例如设备新登录、支付成功、退款完成、导出就绪；
- 缺少设备/PC 详情页，信息和操作全部堆在表格；
- 缺少当前客户端版本与最新版本的对比，但 Web 仍不应提供 Agent 自动升级按钮；
- 时间全部显示 UTC，普通用户更需要本地时区，同时保留 UTC 详情；
- 后端能力未启用时，页面应提前隐藏或禁用操作，而不是提交后才报 503。

## 8. 管理员运行与安全控制台

主入口 `/admin` 当前包含：

| 分区 | 当前功能 | 产品评价 |
| --- | --- | --- |
| 运行概览 | Schema、用户、管理账号、设备、PC、会话、套餐、订阅计数及近期安全事件 | 基础可用，但缺少趋势和告警 |
| 连接路由 | 设备名、类型、信任、运行会话数、输出序号、最后在线 | 符合内容盲边界；固定最多 100 条 |
| Docker 部署 | Compose 与安全边界说明、Schema 信息 | 更像说明文档，不是真正部署观测 |
| 系统版本 | Server 构建身份、协议版本、Android/Windows AppShip 发布信息 | 已实现；当前 Server 元数据未知且 AppShip 读取失败 |
| 安全审计 | 操作、目标类型、脱敏目标、结果、Trace、时间 | 已实现；固定最多 100 条，缺少筛选和导出流程 |
| 订阅与权益 | 套餐数和有效订阅数 | 有直接路由，但主导航不明显，信息较少 |
| 身份与安全 | OIDC Authority、身份服务和首个管理员说明 | 以说明和跳转为主 |
| 账号与角色 | 账号引用、角色、状态、设备数；SUPER_ADMIN 可修改角色和停启账号 | 已实现；固定最多 200 条，无搜索和详情 |

当前“运行概览”来自数据库聚合，不等于完整的 API、Valkey、对象存储、Keycloak、AppShip、支付渠道、后台任务健康视图。Docker 页面也不会实际执行容器控制，这是正确的安全选择，但页面名称容易让管理员误以为这里能完成部署管理。

## 9. 管理员商业化控制台

入口 `/admin/commerce` 当前有 10 个一级分区、32 个表单和 18 张表格，功能覆盖面很高。

| 分区 | 当前功能 | 状态与问题 |
| --- | --- | --- |
| 套餐草稿 | 新建/编辑草稿、发布前校验、发布 Catalog | 已实现；Feature Flags 和渠道映射不在页面管理 |
| 订单报表 | 时间、账号、订单、状态筛选，游标分页，MFA 审计 CSV 导出 | 已实现 |
| 账务一致性 | 查找订单、交易、退款、权益之间的不一致 | 已实现，只读 |
| 对账差异 | 差异队列、状态转换、操作备注、乐观版本和幂等 | 已实现 |
| 注册与邀请码 | OPEN/邀请码/关闭策略，批次、生成、停用、代码、核销记录 | 已实现；当前部署未使用 |
| 兑换码 | 赠送规则、批次、代码生成/停用和核销历史 | 已实现；当前部署未使用 |
| 人工权益 | 按账号赠送限时权益、撤销、重新聚合 | 已实现；与订单支付状态隔离 |
| 订单与退款 | 全部订单、主动查单、重试履约、安全关单、创建和确认全额退款 | 已实现；当前没有真实渠道和订单 |
| 支付事件与对账 | 交易、脱敏通知、发起对账、对账任务 | 已实现；当前渠道未启用 |
| 支付渠道 | 支付宝/微信场景、版本化配置、Secret 引用、验证、启用、停用、证书健康 | 已实现；当前记录均未配置 |

### 9.1 商业化后台的优点

- 邀请码和兑换码完全分离；
- 明文代码只在生成响应显示一次；
- 价格由 Server 按已发布 Catalog 重新计算；
- 支付回调和主动查单才是权威结果；
- 人工权益不会伪造已支付订单；
- 退款、履约和对账有独立状态机；
- Secret 只保存引用，不回显原文；
- 报表查询有范围和条数限制。

### 9.2 商业化后台的产品缺口

- 导航按数据表和技术模块组织，运营人员完成一个任务需要跨多个分区；
- 创建批次、生成代码、查看库存和核销记录缺少统一批次详情页；
- 大量危险操作以行内表单呈现，容易误操作，也不利于移动窗口；
- 除订单报表和一致性外，多数列表只有固定上限，没有搜索、筛选和分页；
- 支付配置需要理解 Secret 引用格式，缺少按支付宝/微信区分的配置向导；
- 缺少证书到期、回调连续失败、履约积压、对账异常的任务中心；
- 当前退款是“创建 + 确认”流程，但还没有按金额和风险分级的双人审批矩阵；
- 当前 ADMIN 权限较宽，无法只授予客服查单、财务退款、运营发码等单独权限；
- 没有营销活动、渠道来源、转化率和邀请码/兑换码使用漏斗。

## 10. 支撑客户端的 Server API

以下属于同一 Server 的能力，但不是浏览器页面。产品说明中需要明确，避免把“Server 已支持”误解为“Web 有入口”。

| API 领域 | 当前能力 |
| --- | --- |
| 设备身份 | 设备注册、自信任、列表、撤销、配对挑战 |
| PC Agent | PC 注册/更新、平台和能力上报、授权 Grant |
| 文件操作 | 创建、领取、续租、上传、完成、取消文件任务 |
| Agent 自动升级 | 资格检查、创建、领取、进度、完成、取消；产品入口仅 Android |
| 会话 | 会话注册、列表、订阅、删除和生命周期管理 |
| 控制租约 | 获取、续租、释放、强制释放，支持单人/接管/协同策略基础 |
| 加密历史 | 上传、提交、分页读取和删除加密历史 |
| Realtime | 认证 WebSocket Relay，Server 只处理路由和密文 |
| 计费 | Google Play 验证/恢复、Web 订单、支付宝/微信回调、兑换和权益 |
| 用户隐私 | 导出、下载、注销预检、申请、查询和取消 |
| 管理运营 | 注册策略、邀请码、兑换码、订单、退款、渠道、套餐、报表和对账 API |

## 11. 技术与体验评价

### 11.1 值得保留

- 服务端渲染，首次页面开销小，公开页面当前本地网络响应约几十毫秒；
- 客户端 JavaScript 主要用于主题、注册和确认，没有大型前端运行时；
- 管理页按 section 加载数据，避免每次请求执行全部后台查询；
- 查询普遍有条数、时间范围或游标限制；
- AppShip 请求有超时、响应大小、字段和签名状态校验；
- CSS 已覆盖响应式、键盘焦点、粗指针和减少动画；
- 页面明确标注终端正文不可见。

### 11.2 需要优化

- 四套页面壳和多份 CSS 已出现视觉与交互分叉；
- 商业后台模板和处理器过大，后续需求会提高回归成本；
- 除注册外几乎没有异步增强，长任务完全依赖刷新；
- 页面“是否显示按钮”与运行时能力不是统一来源；
- 状态页与 Docker 页更像静态说明，不能帮助定位用户可感知故障；
- 失败页能安全隐藏内部错误，但普通用户缺少下一步恢复建议和稳定错误编号；
- 缺少完整无障碍自动验收、真实窄窗口验收和运营任务可用性测试记录。

## 13. 优化路线图

### P0：修正“显示可用”和“实际可用”的不一致

1. 修复 AppShip split-horizon DNS 读取：复用精确私网 IP 白名单和 TLS 主机校验，不放宽通用 SSRF 策略；
2. 下载、版本、状态和管理员系统版本四处共用同一发布可用性结果；
3. 支付方式由“已启用且验证健康”的渠道动态生成，未配置时不允许创建订单；
4. 建立统一 Runtime Capability 模型，页面按 `payment_available`、`account_deletion_available`、`data_export_available`、`release_distribution_available` 展示；
5. 本地和正式镜像都注入可识别的 Server version、revision、created，禁止生产环境显示 `dev/unknown`；
6. 明确当前注册运营策略：若仍处于受控测试，先生成管理员邀请码批次，再把生产策略切换到 `INVITE_REQUIRED`；
7. 状态页至少准确区分“未配置、不可用、未公开、正常”，不要用“未公开”掩盖产品功能尚未启用。

P0 验收标准：

- AppShip 可用时下载和版本页连续展示 Android/Windows 已验证稳定版本；
- AppShip 不可用时不展示未验证链接，并显示最后成功检查时间；
- 支付渠道未启用时用户看不到可提交的支付方式；
- 注销处理器未启用时页面明确显示“当前未开放”且没有提交按钮；
- 系统版本页能定位到唯一 Server 构建。

### P1：统一用户体验和核心任务效率

1. 合并 `/account` 与 `/commerce` 的信息架构和视觉壳；
2. 合并 `/admin` 与 `/admin/commerce` 导航，按业务任务分组；
3. 概览页改为“状态 + 待办 + 最近变化”，而不只是数量卡片；
4. 为设备、PC、会话、账号、审计和代码批次补充搜索、筛选、游标分页；
5. 把表格行内危险表单改为“更多菜单 + 详情抽屉/确认对话框”；
6. 为订单、支付、导出、注销、对账等任务增加有限轮询或 SSE，自动更新状态；
7. 增加当前设备标识、设备/PC 重命名、版本新旧对比和本地时区；
8. 统一错误呈现：用户语言、错误类别、可执行恢复动作和可复制 Trace ID。

不需要为这些能力引入大型 SPA。可使用原生 JavaScript、局部 HTML 端点或轻量渐进增强完成。

### P2：提升商业化与运营成熟度

1. 为邀请码、兑换码建立批次详情页：库存、使用趋势、渠道、生成、一次性下载和停用；
2. 支付配置改为 Provider 向导，分别校验支付宝和微信所需字段、证书和回调；
3. 建立运营任务中心：支付回调异常、履约积压、退款待确认、对账差异、证书到期；
4. 将角色升级为权限集合，至少拆分客服、运营、财务、审计、安全管理员；
5. 退款引入金额阈值、申请人与审批人隔离和双人审批；
6. 套餐页支持功能对比、版本预览、定时发布、回退影响预览；
7. 订单详情增加完整但脱敏的业务时间线和操作记录；
8. 为注册恢复、账号注销、隐私导出增加管理员只读任务状态页。

### P3：增长、品牌与长期治理

1. 建立注册、首台 PC、首个会话、付费和续费漏斗；
2. 增加邀请码和兑换码渠道归因，但不保存不必要的个人信息；
3. 增加公告、维护窗口和公开事件历史；
4. 增加中文/英文国际化，避免当前中英文术语混杂；
5. 抽取统一 Web Design Tokens 和组件库，与 Android/Avalonia 使用同一品牌规范；
6. 建立 WCAG 2.2 AA、键盘、读屏、窄窗口和高对比度自动验收；
7. 增加隐私政策、服务条款、退款政策和支持入口。

## 14. 建议关注的产品指标

| 领域 | 建议指标 |
| --- | --- |
| 公开分发 | 下载元数据可用率、下载成功率、哈希校验失败率 |
| 激活 | 注册到首台 PC、首台 PC 到首个会话的转化和耗时 |
| 连接 | 在线 PC、重连成功率、会话恢复成功率，不采集终端正文 |
| 商业化 | 下单转化、支付成功、履约延迟、退款率、渠道失败分类 |
| 准入 | 邀请码生成、使用、过期、耗尽和注册成功率 |
| 运营 | 待处理异常数量、平均处理时长、重复操作拦截次数 |
| 安全 | MFA 覆盖率、设备撤销、敏感操作拒绝、账号停用事件 |
| 隐私 | 导出完成时长、注销阻塞原因、冷静期取消率和最终完成率 |

所有指标必须继续遵守内容盲原则，不记录终端正文、命令、Token、Secret 或不必要的个人信息。

## 15. 最终产品判断

当前 Server Web 的后端能力已经达到“可支撑内测运营”的宽度，安全边界也比一般早期产品完整。但面向用户和运营人员的产品化仍处于“能力控制台”阶段：入口分散、运行配置未统一反映到 UI、异步任务依赖手动刷新、商业后台过度表格化。

下一阶段不应继续横向堆叠更多一级页面。建议先完成 P0 的真实性修正，再做 P1 的统一账号中心和统一管理员中心。只有当现有能力能够被准确发现、正确操作、及时反馈和审计恢复后，再进入更细的商业化权限、运营自动化和增长分析。

### 15.1 本轮实施后状态

截至 2026-08-27，P0 的能力真实性以及 P1 的统一门户主干已经完成：公开首页、统一用户中心、动态支付能力、动态管理安全入口、服务邮箱、注册邮箱验证、用户资料修改和 Web-only MFA 均已落入源码。管理中心两套内容模板仍存在，但已共享同一套导航、顶栏账号菜单和响应式设计，因此 URL 和权限域保持兼容，用户不再面对两个割裂的后台入口。

仍建议继续投入的主要是 P1 后半段和 P2 产品化工作：表格详情抽屉、行内危险操作收敛、搜索与游标分页、异步任务自动刷新、支付配置向导和运营待办中心。这些不会阻塞现有功能的正确性，但会决定管理效率和日常运营体验。
