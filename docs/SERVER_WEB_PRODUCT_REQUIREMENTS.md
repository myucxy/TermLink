# TermLink Server Web 产品与商业化控制面需求

文档版本：1.1
状态：实现与验收基线；代码已落地，是否对外上线仍取决于生产配置、发布与部署
更新日期：2026-08-27
适用范围：TermLink Server API、用户 Web、管理员 Web、身份注册、套餐权益与支付服务

## 1. 文档目的

本文重新定义 TermLink Server Web 的产品定位、页面结构和服务端商业化能力，并把以下新增需求纳入统一设计：

- 注册可以切换为邀请码准入，不再允许任意用户注册；
- 管理员可以生成、停用和审计邀请码；
- 兑换码可以向已注册用户赠送套餐或限时权益；
- Web 支持支付宝与微信支付，并提供安全的支付渠道配置页面；
- 普通用户与管理员拥有不同的页面、权限和操作边界；
- 邀请、兑换、订单、支付回调、权益发放和退款均可审计、可幂等、可补偿。

本文同时作为产品、实现和验收基线。文中的“已实现”仅表示当前源码及自动化测试具备该能力，不表示已经发布、部署或启用真实商户支付。

## 3. 产品定位与范围

### 3.1 Server Web 的定位

Server Web 是 TermLink 的“账号与控制策略中心 + 商业化与运营后台”，负责：

- 用户账号、安全、设备、PC 和会话元数据管理；
- 套餐、订阅、订单、兑换和权益查询；
- 管理员对注册准入、邀请码、兑换码、支付渠道和审计的运营管理；
- 服务端运行状态、连接路由和版本分发的可观测入口。

### 3.2 明确不做的能力

Server Web 不承担以下功能：

- 不展示或解密终端正文；
- 不提供网页版终端控制；
- 不提供网页版远程文件浏览；
- 不提供 Docker 任意命令执行器或服务器通用 Shell；
- 不提供 Android 才允许触发的 Windows Agent 自动升级入口；
- 不以浏览器返回的“支付成功”页面作为发放权益的依据。

终端内容继续遵循端到端加密边界。Web 只能展示会话 ID、状态、时间、PC、控制策略等必要元数据。

## 4. 用户角色与权限模型

### 4.1 普通用户

普通用户只能管理属于自己的数据：

- 查看和维护账号资料；
- 查看、命名和撤销自己的 Android 设备与 PC；
- 查看自己的会话元数据与控制记录；
- 管理自己的会话控制策略；
- 查看套餐、订阅、权益和订单；
- 核销兑换码；
- 查看自己的登录、安全和高风险操作记录；
- 请求数据导出或账号删除。

普通用户不能生成邀请码、批量生成兑换码、修改支付配置、查看其他用户、操作服务端容器或触发 Agent 自动升级。

### 4.2 管理员角色

管理员权限采用 RBAC，并按最小权限拆分：

| 角色 | 主要权限 | 明确禁止 |
| --- | --- | --- |
| `AUDITOR` | 只读查看运行状态、订单摘要、支付事件、配置元数据和审计日志 | 修改配置、生成码、退款、封禁账号、查看 Secret |
| `ADMIN` | 用户运营、邀请码和兑换码批次、订单支持、套餐草稿、异常履约重试 | 修改支付 Secret、授予角色、关闭审计、执行系统级配置 |
| `SUPER_ADMIN` | 支付渠道配置、角色管理、账号状态、注册策略、系统安全策略和高风险运营操作 | 仍不能读取私钥明文或绕过审计 |

`SUPER_ADMIN` 不是无约束的后门。服务端仍必须执行资源范围、状态机、幂等和审计校验。

### 4.3 高风险操作共同要求

以下操作至少要求最近一次登录验证；生产环境建议同时要求 MFA：

- 修改注册策略；
- 创建或批量导出邀请码、兑换码；
- 修改、启用或停用支付渠道；
- 退款、人工调整权益、封禁账号；
- 修改管理员角色或安全策略。

每个高风险请求还必须具备：

- CSRF 防护；
- 操作原因；
- 幂等键；
- 操作者、目标、结果和前后差异审计；
- 必要时的二次确认或双人复核；
- 不包含凭据明文的脱敏日志。

## 6. 注册准入与邀请码

### 6.1 全局注册策略

服务端提供以下三种注册模式：

| 模式 | 行为 |
| --- | --- |
| `OPEN` | 允许符合风控规则的用户直接注册 |
| `INVITE_REQUIRED` | 注册必须提交有效邀请码 |
| `CLOSED` | 暂停新注册，既有用户仍可登录 |

生产环境默认建议使用 `INVITE_REQUIRED`。注册策略由 `SUPER_ADMIN` 修改，修改后立即生效并写入审计。前端不得通过隐藏邀请码输入框自行决定注册模式。

### 6.2 邀请码业务规则

邀请码只用于取得注册资格，不等同于兑换码。一个邀请码可以配置：

- 所属批次和活动名称；
- 最大总使用次数；
- 同一账号或邮箱最多使用次数，默认一次；
- 生效时间和失效时间；
- 允许的完整邮箱或邮箱域；
- 可选的注册后默认赠送套餐规则；
- 创建原因、备注和来源渠道；
- `DRAFT`、`ACTIVE`、`DISABLED`、`EXPIRED`、`EXHAUSTED` 状态。

邀请码使用高熵随机值生成，不能使用顺序号、短数字或可预测前缀。数据库只保存 `code_hash` 和用于后台辨识的非敏感短前缀，不保存可兑换的明文。

生成后的明文只允许在创建响应中显示一次，并支持当次下载。响应结束后，后台只能导出邀请码状态和使用记录，不能再次导出明文；需要新明文时必须生成新批次。

### 6.3 注册流程

注册流程固定为：

1. 客户端读取公开注册策略；
2. 用户提交注册资料和必要的邀请码；
3. 服务端规范化邮箱，执行频率限制、风控和邀请码候选匹配；
4. 服务端为该邀请码创建短时 `RESERVED` 使用占位；
5. 服务端调用 Keycloak 创建身份；
6. 创建成功后，事务化确认邀请码核销、用户映射和可选赠送权益；
7. 任一步失败均执行释放占位、删除孤儿身份或后台补偿；
8. 最终结果通过审计和 Outbox 记录，保证可追踪与可重试。

不能在持有数据库事务期间等待 Keycloak 网络调用。应使用预约、确认、释放和补偿组成的 Saga，防止出现“邀请码已消耗但账号未创建”或“账号已创建但邀请码未消耗”。

并发使用最后一个名额时只能有一个请求成功。邀请码的计数、预约和最终核销必须通过数据库约束或行级锁保证原子性。

### 6.4 防枚举与隐私

公开校验接口不能向未登录用户区分“不存在、已过期、已耗尽或被禁用”，避免攻击者枚举有效邀请码。外部可以统一返回“邀请码无效或不可使用”，详细原因只写安全审计。

邮箱限制应匹配规范化后的注册邮箱；若系统要求邮箱验证，账号在邮箱验证完成前不能获得正式访问权限。

### 6.6 建议 API

公开或注册流程接口：

- `GET /v1/registration-policy`
- `POST /v1/auth/invitations/validate`
- `POST /v1/auth/register`，新增可选字段 `invitation_code`，是否必填由服务端策略决定

管理员接口：

- `GET /v1/admin/registration-policy`
- `PATCH /v1/admin/registration-policy`
- `GET /v1/admin/invitation-batches`
- `POST /v1/admin/invitation-batches`
- `POST /v1/admin/invitation-batches/{batch_id}/generate`
- `POST /v1/admin/invitation-batches/{batch_id}/disable`
- `GET /v1/admin/invitation-codes`
- `POST /v1/admin/invitation-codes/{code_id}/disable`
- `GET /v1/admin/invitation-redemptions`

建议错误码：

- `REGISTRATION_CLOSED`
- `INVITATION_REQUIRED`
- `INVITATION_INVALID`
- `INVITATION_EXPIRED`
- `INVITATION_EXHAUSTED`
- `INVITATION_EMAIL_MISMATCH`

未登录调用的错误信息可以统一，管理员审计和内部指标保留精确分类。

## 7. 兑换码与赠送套餐

### 7.1 与邀请码的边界

| 类型 | 使用人 | 作用 | 使用时机 |
| --- | --- | --- | --- |
| 邀请码 | 未注册用户 | 获得注册资格，可选附带一次赠送 | 注册过程中 |
| 兑换码 | 已登录用户 | 获得套餐、时长或指定权益 | 注册完成后 |

两个体系必须使用独立的数据表、API、后台页面、错误码和风控计数。任何邀请码都不能直接传给兑换接口，兑换码也不能绕过注册策略。

### 7.2 兑换码能力

兑换批次可以配置：

- 赠送的套餐版本或权益集合；
- 赠送天数、自然月数或固定到期日；
- 总核销次数和单账号核销次数；
- 生效、失效时间；
- 活动、渠道、备注和外部关联号；
- 是否允许与现有赠送叠加；
- 对当前套餐、用户范围或新老用户的适用规则；
- `DRAFT`、`ACTIVE`、`DISABLED`、`EXPIRED`、`EXHAUSTED` 状态。

兑换前页面应显示“将获得什么、何时生效、何时到期、是否影响现有订阅”，用户确认后再核销。

### 7.3 权益叠加规则

默认规则如下：

- 同套餐赠送：从 `max(当前时间, 当前同类赠送到期时间)` 开始延长；
- 更高套餐赠送：立即生效，保存赠送结束后的恢复计划；
- 更低套餐赠送：默认拒绝，或按明确配置排队，不能直接降低现有权益；
- 自动续费订阅继续作为长期来源，赠送权益只在指定时间段内覆盖；
- 退款、撤销或活动作废时只撤销对应来源，不删除其他来源产生的权益；
- 最终有效权益由聚合器根据所有有效 Grant 计算，不能只覆盖 `entitlements` 表中的一行。

### 7.4 事务、幂等和风控

兑换请求必须在一个数据库事务中完成以下操作：

1. 校验代码、账号、时间、适用范围和叠加规则；
2. 原子占用剩余次数；
3. 创建唯一核销记录；
4. 创建不可变的权益来源 Grant；
5. 更新账号聚合权益；
6. 写入 Outbox 和审计。

同一请求的重试必须返回同一结果，不得重复增加时长。并发使用最后一个名额时只能成功一次。

| `redemption_codes` | `id`, `batch_id`, `code_hash`, `code_prefix`, `max_uses`, `used_count`, `valid_from`, `valid_until`, `status` |

`entitlements` 可以继续作为快速查询的聚合结果，但 `entitlement_grants` 才是权益来源和恢复计算的事实记录。

## 8. 统一订单与支付架构

### 8.1 支付来源标准化

目标支付来源使用明确枚举：

- `GOOGLE_PLAY`
- `ALIPAY`
- `WECHAT_PAY`
- `REDEMPTION`
- `MANUAL`

不再把笼统的 `WEB` 作为新的最终 Provider。迁移阶段可以把已有 `WEB` 数据保留为兼容别名，但新订单必须记录真实渠道和支付场景。

### 8.2 支付闭环

标准支付流程为：

1. 客户端选择已发布且当前可售的套餐；
2. 服务端重新计算价格、币种和权益，创建订单；
3. 服务端调用支付宝或微信统一下单，返回二维码、跳转地址或支付参数；
4. 客户端展示待支付状态并轮询订单，不能本地声明成功；
5. 支付渠道向独立回调地址发送异步通知；
6. 服务端验签、解密、校验商户和金额，持久化通知并推进支付交易；
7. 履约服务幂等创建订阅和权益 Grant；
8. 未收到通知或处理失败时由主动查单和后台任务补偿；
9. 超时未支付订单关闭；退款后按对应来源调整权益。

支付异步通知或主动查单结果是支付状态的权威来源。浏览器 Return URL 只用于改善页面体验。

### 8.3 状态机

订单状态：

```text
CREATED -> PENDING_PAYMENT -> PAID -> FULFILLING -> FULFILLED
    |              |           |          |
    +-> CLOSED <---+           +-> FAILED +-> FAILED
                               |
                               +-> REFUNDING -> REFUNDED
```

支付交易状态：

```text
INITIATED -> PENDING -> SUCCEEDED
     |          |          |
     +-> FAILED +-> CLOSED +-> REFUNDED
```

状态只能按服务端允许的方向推进。重复、延迟或乱序通知不能把已退款订单恢复为已支付，也不能重复履约。

### 8.4 核心数据模型

| 表 | 关键字段 |
| --- | --- |
| `payment_channels` | `id`, `provider`, `scene`, `enabled`, `active_version_id`, `health_status` |
| `payment_channel_versions` | `id`, `channel_id`, `environment`, `public_config_json`, `secret_refs_json`, `created_by`, `validated_at` |
| `orders` | `id`, `order_no`, `user_id`, `plan_version_id`, `amount_minor`, `currency`, `status`, `expires_at` |
| `payment_transactions` | `id`, `order_id`, `provider`, `provider_trade_no_hash`, `status`, `amount_minor`, `requested_at`, `paid_at` |
| `payment_notifications` | `id`, `provider`, `notification_id_hash`, `signature_result`, `processing_state`, `received_at` |
| `refunds` | `id`, `order_id`, `transaction_id`, `refund_no`, `amount_minor`, `reason`, `status`, `provider_ref_hash` |
| `reconciliation_runs` | `id`, `provider`, `period`, `status`, `result_summary`, `started_at`, `completed_at` |

金额一律使用最小货币单位的整数，例如人民币分；禁止使用浮点数。首期币种可只允许 `CNY`，但数据模型仍应显式保存币种。

## 9. 支付宝接入

### 9.1 支付场景

首期建议优先实现适合 PC Web 的当面付二维码；若需要浏览器跳转，再增加电脑网站支付。每种场景使用独立的 `scene`，不能只依靠前端参数临时切换。

### 9.2 配置字段

- App ID；
- 商户/卖家标识；
- 应用私钥的 Secret 引用；
- 支付宝公钥或证书引用；
- 网关地址；
- Notify URL；
- Return URL；
- RSA2 签名算法；
- 沙箱或生产环境；
- 证书序列号与到期时间。

### 9.3 回调校验

支付宝异步通知必须：

1. 使用官方规则执行 RSA2 验签；
2. 校验 App ID、卖家、商户订单号、金额和币种；
3. 根据渠道通知 ID 和交易号摘要去重；
4. 只允许合法状态迁移并幂等履约；
5. 按支付宝协议返回准确的成功或失败响应；
6. 验签或金额校验失败时记录安全事件，不更新订单权益。

## 10. 微信支付接入

### 10.1 支付场景

采用微信支付 API v3。PC Web 首期建议使用 Native 支付二维码；H5 和 JSAPI 在具备相应商户能力、域名配置和产品需求后按独立场景启用。

### 10.2 配置字段

- App ID；
- 商户号 `mchid`；
- 商户证书序列号；
- 商户 API 私钥的 Secret 引用；
- API v3 Key 的 Secret 引用；
- 微信支付平台证书或公钥引用；
- Notify URL；
- 已启用的 Native、H5 或 JSAPI 场景；
- 生产或受控测试环境标识。

### 10.3 回调校验

微信支付通知必须：

1. 使用平台证书或公钥验证 HTTP 签名和时间窗口；
2. 使用 API v3 Key 对资源执行 AES-256-GCM 解密；
3. 校验商户号、App ID、商户订单号、金额和币种；
4. 根据通知 ID 和交易号摘要去重并幂等履约；
5. 支持平台证书下载、轮换、过期预警和旧证书宽限；
6. 解密、验签或金额校验失败时拒绝更新订单并告警。

## 11. 支付渠道配置页面

### 11.1 页面位置与可见范围

建议使用独立路由 `/admin/payment-channels`。`AUDITOR` 只读，`ADMIN` 可查看健康和错误但不能修改 Secret，只有通过 Step-up/MFA 的 `SUPER_ADMIN` 可以创建、验证、启用或停用配置。

### 11.2 页面展示

每个渠道卡片显示：

- 是否启用及当前环境；
- 支付场景；
- 脱敏后的 App ID、商户号；
- 证书序列号和到期时间；
- Notify URL；
- 当前配置版本；
- 最后验证时间；
- 最后一次有效 Webhook 时间；
- Webhook 健康状态；
- 最近一次脱敏错误码和关联追踪 ID。

### 11.3 Secret 管理

- 私钥、API v3 Key 等 Secret 不以数据库明文保存；
- 优先使用 Docker Secret 或外部 Secret Manager；
- 数据库和页面只保存 Secret 文件名、Secret ID 或版本引用；
- API 永远不回显已保存 Secret，即使是 `SUPER_ADMIN`；
- 配置页不提供私钥下载；
- 日志、HTML、前端状态和监控标签中不能出现 Secret；
- Secret 轮换使用新版本，验证通过后原子启用，并保留必要的旧证书回调宽限期；
- 非 Secret 配置需要版本化，可回滚到已验证版本。

“测试配置”只允许执行格式、签名、证书、网关连通性和受支持的官方查询验证，不能产生真实扣款。

## 12. 用户订单与管理员支付页面

### 12.1 用户订单页面

用户可以查看：

- TermLink 订单号；
- 套餐名称、周期和权益摘要；
- 金额和币种；
- 支付渠道；

- 当前订单、履约和退款状态；
- 未支付订单的重新支付和取消操作。

页面不得展示 Provider 原始 Token、完整外部交易凭据、签名、Secret 或未脱敏的通知正文。

### 12.2 管理员订单与支付页面

管理员页面支持：

- 按订单号、账号、渠道、状态和时间查询；
- 对单个异常订单主动查单；
- 在确认支付成功后安全重试履约；

## 13. 安全、隐私与合规要求

### 13.1 邀请码和兑换码

- 使用密码学安全随机数和足够熵；
- 只存哈希和短辨识前缀；
- 提交和生成接口分别限流；
- 同账号、IP、设备指纹的异常失败需要告警；
- 批量生成和一次性明文下载需要强认证和审计；
- 后台搜索不能根据短前缀还原有效代码；
- 日志只记录代码 ID，不能记录用户提交的明文。

### 13.2 支付

- 订单号由服务端生成且不可预测；
- 价格和套餐由服务端按已发布目录重新计算；
- 回调不依赖登录 Cookie，并使用独立限流策略；
- 验签需校验时间窗口、证书和防重放字段；
- 原始通知按最小化原则保存，确需留存时加密并设置保留期；
- 不保存银行卡、支付密码或用户的支付账户凭据；
- 退款默认需要二次确认，高金额可要求双人复核；
- 所有 Provider 请求使用稳定的请求 ID 和可关联追踪 ID；
- 密钥、Token、证书私钥和个人信息必须在日志中脱敏；
- 定期检查证书过期、Webhook 连续失败和订单权益不一致。

### 13.3 管理与审计

审计事件至少记录：

- 操作者用户和设备；
- 角色与认证强度；
- 操作、资源类型和资源 ID；
- 操作原因；
- 请求追踪 ID 和幂等键摘要；
- 前后状态差异；
- 成功、拒绝或失败结果；
- 时间和脱敏来源地址。

审计记录不可被普通管理员修改。审计详情仍需遵循个人信息最小化，且绝不保存终端正文或支付 Secret。

## 14. 可靠性、补偿与可观测性

### 14.1 必须存在的后台任务

- 释放超时的邀请码注册预约；
- 检查 Keycloak 孤儿身份和未完成注册 Saga；
- 关闭超时未支付订单；
- 主动查询长时间 `PENDING` 的支付交易；
- 重试已支付但未完成的权益履约；
- 处理退款结果；
- 聚合订单、订阅与权益一致性；
- 运行支付宝、微信支付对账；
- 检查证书到期和 Webhook 健康。

后台任务必须可重入，任务重试不能重复核销、发放或退款。

### 14.2 指标和告警

建议至少监控：

- 注册成功率及各内部失败分类；
- 邀请码预约超时和并发冲突；
- 兑换成功率、重复提交和库存耗尽；
- 订单创建、支付成功、履约成功和退款时延；
- Webhook 验签失败、重复、乱序和处理积压；
- 主动查单恢复的订单数量；
- 支付渠道连续错误率和证书剩余天数；
- 订单、订阅、Grant 与聚合权益的不一致数量。

监控标签不能使用完整邮箱、邀请码、兑换码、外部交易号或其他高基数敏感信息。

## 15. 兼容与迁移策略

### 15.1 注册兼容

- 服务端保持 `POST /v1/auth/register` 路径稳定；
- `OPEN` 模式下旧客户端可以不提交 `invitation_code`；
- 切换到 `INVITE_REQUIRED` 后，旧客户端应收到结构化 `INVITATION_REQUIRED`，并提示升级或前往 Web 注册；
- 不允许为了兼容旧客户端绕过服务端注册策略。

### 15.2 计费兼容

- 保留现有 Google Play 验证和恢复购买能力；
- 现有 `WEB` Provider 数据通过迁移映射到兼容记录，新订单使用明确 Provider；
- 已有 `subscriptions` 和 `entitlements` 数据迁移为来源清晰的 Grant 或建立兼容映射；
- 客户端仍以账号权益接口作为统一查询入口，不直接依赖支付宝或微信状态；
- 新字段先做到服务端向后兼容，再逐步升级 Web、Android 和 PC 客户端。

### 15.3 发布原则

数据库迁移遵循扩展、回填、切换、清理顺序。新表和可空字段先上线，后台双写和数据校验稳定后再切换读路径；禁止在同一发布中直接删除旧 Provider 或旧权益字段。

## 17. 验收测试清单

### 17.1 注册与邀请码

- `OPEN`、`INVITE_REQUIRED` 和 `CLOSED` 三种模式行为正确；
- 并发消耗最后一个邀请码名额时只有一个注册成功；
- Keycloak 创建失败后邀请码预约可释放；
- Keycloak 成功但数据库确认失败时可以补偿或恢复；
- 已禁用、过期、耗尽和邮箱不匹配的邀请码均被拒绝；
- 公共错误不会泄露邀请码是否存在；
- 明文邀请码不出现在数据库、日志、指标和后续查询响应中；
- 旧客户端在邀请模式下获得明确、可升级处理的错误。

### 17.2 兑换码与权益

- 同一请求重试不会重复延长套餐；
- 同一账号重复核销和多人并发核销符合批次规则；
- 并发使用最后一个兑换次数时只成功一次；
- 同套餐、更高套餐、更低套餐和自动续费并存规则正确；
- 赠送结束后恢复到正确的付费或免费权益；
- 撤销一个 Grant 不影响其他合法权益来源；
- 兑换、权益聚合和 Outbox 写入保持事务一致。

### 17.3 支付与订单

- 客户端篡改套餐、金额或币种不能创建错误价格订单；
- 支付宝与微信支付的重复、乱序、延迟和伪造回调均安全处理；
- 回调中的 App ID、商户号、订单号、金额或币种不一致时不发权益；
- 支付成功但数据库或履约暂时失败时可由后台任务恢复；
- 未收到通知时可通过主动查单恢复；
- 相同支付只创建一个订阅和一个对应权益来源；
- 超时未支付订单可以安全关闭，已支付订单不会被误关；
- 全额和允许的部分退款状态、金额及权益处理正确；
- 对账能发现渠道、订单和权益的不一致并产生可操作告警。

### 17.4 配置、权限与安全

- `AUDITOR`、`ADMIN`、`SUPER_ADMIN` 的读写边界符合权限矩阵；
- 高风险操作缺少 Step-up、MFA、CSRF、原因或幂等键时被拒绝；
- Secret 不出现在 API、HTML、前端缓存、日志、追踪和导出文件中；
- 配置验证失败时不能启用，旧有效版本继续工作；
- 证书轮换期间新旧合法回调按策略正常处理；
- 退款、人工权益和角色变更均有完整审计；
- 普通用户不能访问其他账号的订单、核销和权益；
- Web 页面和 API 都不能读取或展示终端正文。

## 18. 上线前必须确认的业务项

以下内容不能由技术实现自行猜测，应在对应阶段上线前由产品和运营确认：

1. 生产注册默认是否正式采用 `INVITE_REQUIRED`，以及首批邀请码发放对象；
2. 邀请码附带赠送与兑换码赠送能否叠加；
3. 套餐价格、周期、退款规则、发票和税务处理；
4. 支付宝采用当面付、电脑网站支付或两者同时支持；
5. 微信 Native、H5、JSAPI 的实际商户资质和域名条件；
6. 退款是否需要双人复核及金额阈值；
7. 订单、通知、对账文件和审计记录的法定保留期限；
8. Docker Secret 或外部 Secret Manager 的生产选型；
9. 支付渠道正式商户账号、证书和回调公网地址的交付责任人。

在上述业务项确认前，可以完成通用订单核心、接口契约和受控测试环境，但不能把真实生产支付开关默认设为启用。

当前安全默认：在正式确认按比例退款与权益折算规则之前，Server Web
只接受已履约订单的全额退款。部分退款请求返回冲突，不会出现“退还部分
金额但继续保留完整权益”的不明确状态。
