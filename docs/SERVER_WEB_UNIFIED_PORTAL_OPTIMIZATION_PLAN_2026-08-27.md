# TermLink Server Web 统一门户优化方案

文档版本：1.1

日期：2026-08-27

状态：P0–P3 已实现并通过源码级全量测试；P4 的错误引用、共享导航和账号菜单已完成，详情抽屉、自动轮询及更细分页继续保留为后续体验优化

关联文档：`SERVER_WEB_CURRENT_FUNCTION_AUDIT_AND_OPTIMIZATION_2026-08-27.md`

## 1. 本轮需求解释

本方案将当前需求整合为五个产品目标：

1. 公开首页减法：减少重复登录入口和技术性说明，只保留产品价值、下载和一个账号入口；
2. 登录后一步到位：登录回调直接进入统一用户中心，不再经过“个人中心”中转页；
3. 角色感知：普通用户只看到普通用户功能，管理员通过头像菜单或安全入口切换到管理中心；
4. 统一身份安全：取消独立“管理身份”页面，在用户中心内提供资料、密码、Google 身份验证器和登录会话管理；
5. 账号注册减法：注册只使用用户名、昵称、邮箱、邀请码（策略要求时）和密码，不再采集姓、名；用户名和邮箱均可登录，内部仍使用不可变用户 ID。

文中“Google 身份验证器”按 Google Authenticator、RFC 6238 TOTP 动态验证码理解。

## 2. 最终产品原则

- 普通用户登录后的第一屏永远是自己的用户仪表盘；
- 管理权限不会改变普通用户菜单，只增加头像菜单中的“进入管理中心”；
- 页面菜单由服务端按数据库角色和运行能力生成，不能只用 CSS 隐藏；
- 用户中心与管理中心使用同一套品牌、布局、组件和交互规范；
- 用户名和邮箱是登录别名，昵称只是展示字段，任何可变资料都不能替代内部用户 ID；
- 终端正文、命令、Token、TOTP Secret 和支付 Secret 继续不进入 Web 页面日志或数据库；
- 自定义管理入口只是第二层暴露面收敛，不能替代角色、MFA、最近认证、CSRF、幂等和审计；
- 优先使用服务端渲染和少量渐进增强，不引入大型 SPA。

## 3. 统一信息架构

### 3.1 公开站点

```text
首页
├─ 产品
├─ 下载
├─ 套餐
├─ 安全
├─ 状态
└─ 登录（唯一账号入口）
```

首页不再承担账号控制、管理入口和详细部署文档职责。

### 3.2 登录后的用户中心

统一入口建议使用 `/account`，默认即仪表盘：

```text
用户中心
├─ 仪表盘
├─ 设备与 PC
│  ├─ 移动设备
│  ├─ PC Agent
│  └─ 控制策略
├─ 会话记录
├─ 套餐与权益
├─ 订单与退款
├─ 安全活动
└─ 数据与账号
```

个人资料和身份安全不再作为左侧一级业务菜单堆叠，而是从右上角头像菜单进入：

```text
头像菜单
├─ 个人设置
├─ 登录与安全
├─ 进入管理中心（仅有管理权限时）
└─ 退出登录
```

### 3.3 管理中心

管理中心保持独立权限域，但复用相同页面壳：

```text
管理中心
├─ 总览与待办
├─ 用户与准入
├─ 设备与连接
├─ 产品与分发
├─ 订单与财务
├─ 权益运营
├─ 安全审计
└─ 系统设置
```

角色菜单规则：

| 角色 | 用户中心 | 管理中心入口 | 管理中心能力 |
| --- | --- | --- | --- |
| USER | 完整显示本人相关菜单 | 不显示 | 无 |
| AUDITOR | 与 USER 相同 | 头像菜单显示 | 只读审计、运行与有界报表 |
| ADMIN | 与 USER 相同 | 头像菜单显示 | 日常运营，不含系统安全设置 |
| SUPER_ADMIN | 与 USER 相同 | 头像菜单显示 | 全部管理功能和系统设置 |

管理角色登录后也先进入用户仪表盘，不自动进入后台。

## 4. 页面布局

### 4.1 桌面布局

```text
┌─────────────────────────────────────────────────────────────────┐
│ Logo / TermLink     当前页面             主题  通知  用户头像   │
├──────────────────┬──────────────────────────────────────────────┤
│ 仪表盘           │ 页面标题 / 状态 / 主要操作                   │
│ 设备与 PC        │                                              │
│ 会话记录         │ 功能内容区                                   │
│ 套餐与权益       │                                              │
│ 订单与退款       │                                              │
│ 安全活动         │                                              │
│ 数据与账号       │                                              │
└──────────────────┴──────────────────────────────────────────────┘
```

- 左侧菜单固定但可收起；
- 顶栏固定，显示当前页面、全局状态、主题和头像菜单；
- 右侧功能区只保留当前任务需要的信息；
- 危险操作放在详情页或确认对话框，不在表格内横向堆放输入框。

### 4.2 窄窗口与移动浏览器

- 左侧菜单折叠为抽屉；
- 顶栏保留页面标题和头像；
- 表格优先转换为卡片或主列 + 详情抽屉；
- 操作按钮最小触控尺寸与 Android 产品规范一致；
- 不依赖横向滚动完成关键操作。

## 5. 首页减法方案

### 5.1 保留

- Logo、TermLink 名称和一句产品定位；
- 一个账号入口“登录”；
- 一个主要产品动作“下载客户端”；
- 三项简短能力：终端持续运行、端到端加密、断线恢复；
- 下载、套餐、安全、状态的简洁导航。

### 5.2 删除或移出首页

- Header、Hero 和页尾重复出现的登录按钮；
- 重复的“打开个人中心/打开管理台”按钮；
- 过长的 Docker、Compose、OIDC 和协议实现说明；
- 多次重复的 E2EE 描述；
- 对首次访问没有帮助的内部服务拓扑；
- 作为装饰但占用大量首屏空间的冗长终端输出。

技术细节移到“安全”和后续“文档”页面，部署状态移到管理中心。

### 5.3 登录状态行为

- 未登录访问 `/`：展示精简首页；
- 已登录访问 `/`：直接 303 跳转 `/account`；
- 登录按钮默认回到 `/account`；
- 注册成功后进入登录，登录完成仍回到 `/account`；
- 首页不直接展示管理入口。

## 6. 登录与导航流程

### 6.1 普通登录

```text
首页唯一登录入口
  → Keycloak OIDC + PKCE
  → /auth/callback
  → 校验账号状态与数据库角色
  → /account 用户仪表盘
```

不再经过旧 `/account` 介绍页，也不再跳转 `/account/identity`。

### 6.2 兼容旧地址

| 旧地址 | 新行为 |
| --- | --- |
| `/commerce` | 登录后重定向 `/account` 对应分区 |
| `/account/identity` | 重定向 `/account/security`，不再打开独立 Keycloak Account Console |
| 旧商业化查询参数 | 在兼容期转换到新的用户中心分区 |

兼容重定向保留至少一个发布周期，避免旧书签立即失效。

## 7. 自定义管理入口

### 7.1 产品行为

系统设置提供“管理中心安全入口”配置，例如：

```text
/control/4hPzK8mQvX2sN7aB
```

管理员只填写入口段或由系统生成，不允许填写域名、协议、查询参数和外部 URL。

建议规则：

- 16–64 个字符；
- 仅允许 ASCII 字母、数字、`-`、`_`；
- 不允许 `admin`、`account`、`api`、`auth`、`assets`、`login` 等保留词；
- 默认提供密码学安全随机生成；
- 修改只能由近期完成 MFA 的 SUPER_ADMIN 执行；
- 修改要求原因、二次确认、幂等和审计。

### 7.2 强制规则

当自定义入口生效后：

- `/admin`、`/admin/*` 和旧入口统一返回 404；
- 不做重定向，不透露新入口；
- 只有访问完全匹配的新入口才允许发起管理登录流程；
- 错误入口不会跳转 Keycloak，也不会确认某账号是否具有管理权限；
- 普通用户的 HTML 中不输出管理入口；
- 有管理角色的用户只在已登录后的头像菜单看到入口；
- 管理表单、分页、导出和返回地址全部使用当前动态前缀；
- `/v1/admin/...` API 不随 Web URL 改名，继续依赖强认证与权限；自定义项只控制浏览器管理界面。

### 7.3 安全实现

建议新增单例设置 `web_portal_settings`：

- `admin_route_ciphertext`：用 Server 派生密钥加密；
- `admin_route_hmac`：用于常量时间匹配；
- `admin_route_version`：乐观锁和旧页面失效；
- `updated_by`、`updated_at`：审计来源。

管理路由不应出现在普通应用日志、错误信息、公开状态页或审计正文。管理页面设置 `Referrer-Policy: no-referrer`，不加载第三方资源。反向代理访问日志需要对该路径做脱敏或关闭路径记录。

### 7.4 防止管理员锁死

- 修改前要求再次输入新入口并确认；
- 修改成功页只展示一次新入口并允许安全复制；
- 修改后立即使旧入口失效；
- 提供仅限本机 Docker/终端执行的离线恢复命令，例如重置为默认入口或生成新入口；
- 离线恢复写入独立系统审计，不提供公网“找回管理地址”接口。

自定义入口不能被宣传为密码。即使入口泄露，非管理员、无 MFA 或账号已停用的请求仍必须被拒绝。

## 8. 统一个人设置

头像菜单中的“个人设置”和“登录与安全”使用用户中心同一页面壳。

### 8.1 个人设置

- 头像、昵称、邮箱、用户名和只读用户 ID；
- 用户名创建后不可修改，只作为稳定登录名显示；
- 邮箱修改需要重新验证；
- 语言、主题、时区；
- 不再显示“管理身份”外链。

### 8.2 登录与安全

- 密码修改；
- Google Authenticator/TOTP 状态；
- 绑定、重新绑定和移除身份验证器；
- 恢复代码生成和重新生成；
- 最近登录与活跃浏览器会话；
- 退出其他会话；
- 敏感操作最近认证状态。

身份凭据继续由 Keycloak 持有。TermLink Server 不保存密码、TOTP Seed、二维码内容或恢复代码明文。

## 9. 注册、登录标识与用户 ID

### 9.1 注册字段

新注册页固定为以下字段：

| 字段 | 用途 | 规则 |
| --- | --- | --- |
| 用户名 | 登录标识 | 必填、全局唯一、创建后不可修改 |
| 昵称 | 产品内展示 | 必填、允许重复、可在个人设置修改 |
| 邮箱 | 登录标识、验证和找回密码 | 必填、全局唯一、规范化后比较 |
| 邀请码 | 控制注册准入 | 仅在邀请注册策略开启时显示并要求 |
| 邮箱验证码 | 证明邮箱归属 | 仅在注册邮箱验证开关开启时显示并要求 |
| 密码 | 登录凭据 | 必填，继续遵守 Keycloak 密码策略 |
| 确认密码 | 防止输入错误 | 必须与密码一致 |

不再采集或展示 `first_name`、`last_name`、`firstName`、`lastName`。旧账号中的姓、名数据不拼接成昵称，也不在新页面继续要求用户维护。

昵称规则：

- Trim 后 1–64 个 Unicode 字符；
- 禁止控制字符、换行、双向文本控制符和危险不可见字符；
- 允许重复，不参与登录、账号唯一性、权限判断和审计主体识别；
- Keycloak 使用自定义 `nickname` 用户属性，并通过 OIDC mapper 输出 `nickname` claim；
- 页面展示优先级为 `nickname → preferred_username → email → 用户 ID`。

Keycloak User Profile 需要删除 `firstName` 和 `lastName` 的必填约束，新增可由用户和管理员查看、编辑的单值 `nickname` 属性。新注册 API 使用 `nickname`；旧 API 的 `first_name`、`last_name` 只在一个兼容周期内接受但忽略，不再写入身份资料，随后删除。

### 9.2 用户名、邮箱与昵称的边界

- 登录框统一提示“邮箱或用户名”；
- Keycloak 保持 `loginWithEmailAllowed=true` 和 `duplicateEmailsAllowed=false`；
- Keycloak 设置 `editUsernameAllowed=false`，用户中心、管理中心和 TermLink API 均不提供用户名修改能力；
- 用户名创建后不可修改，避免登录认知、客户端缓存和客服检索产生歧义；
- 邮箱可以修改，但新邮箱验证完成前不替换原邮箱，也不能用新邮箱登录；
- 昵称可以修改，只影响展示；
- 登录失败统一返回相同文案，不泄露用户名或邮箱是否存在。

### 9.3 保留不可变用户 ID

TermLink 继续以 `users.id` UUID 作为数据库主键。该 ID 是账号、设备、PC、会话、订单、权益和审计记录的唯一关联依据：

```text
Keycloak subject
  → keyed subject hash
  → users.id（不可变 UUID 主键）
  → devices / pcs / sessions / orders / audit_events
```

- 用户名、邮箱、昵称变化都不更新 `users.id`；
- 数据库外键不得改为用户名、邮箱或昵称；
- 用户中心可展示只读、可复制的用户 ID，管理查询和客服工单也优先使用该 ID；
- API 和审计使用用户 ID，界面可同时显示昵称和脱敏登录名；
- 身份域迁移时必须显式迁移 Keycloak subject 与现有 `users.id` 的映射，不能为同一用户重新生成业务主键。

### 9.4 注册邮箱验证码

“注册邮箱验证”定义为账号创建前的 6 位一次性验证码，不是创建账号后的邮件链接：

```text
填写用户名、昵称、邮箱和邀请码
  → 请求邮箱验证码
  → 返回通用响应（不泄露邮箱是否已注册）
  → 输入 6 位验证码
  → 服务端原子校验验证码、邀请码和注册请求
  → 创建 Keycloak 用户并写入 nickname
  → 标记邮箱已验证
  → 完成邀请兑换和业务账号关联
```

安全规则：

- 验证码默认 10 分钟有效、单次使用、最多 5 次输入尝试；
- 绑定 `verification_id + normalized_email + purpose`，不能换邮箱复用；
- 数据库只保存带服务端密钥的验证码摘要，不保存明文验证码；
- 按 IP、邮箱摘要、浏览器挑战和全局出口限速，并设置 60 秒重发间隔；
- 返回、日志、指标和审计不记录完整邮箱、验证码或 SMTP 凭据；
- 邀请码在发码前只做无副作用校验，验证码通过后才进入现有邀请预留和注册 Saga；
- 验证码或邮件服务异常时不得绕过验证创建账号；
- 开关关闭时不显示发码和验证码输入框，并明确按“未验证邮箱注册”策略处理。

注册成功只有在验证码已经原子消费、Keycloak 用户创建结果已确认后才能将邮箱标记为已验证。任何超时或结果不确定都进入现有注册恢复流程，不能重复创建用户或重复消耗邀请码。

## 10. 服务邮箱与邮件功能开关

### 10.1 当前基线与目标

当前 Keycloak 配置已经允许邮箱登录，`resetPasswordAllowed=true`，但验收部署未配置 SMTP，`verifyEmail=false`。因此“忘记密码”入口可能可见，实际邮件却无法投递。优化后页面只能展示真实可用的邮件能力。

管理中心的“系统设置 → 服务邮箱”提供：

- 发件人名称、发件邮箱、回复邮箱；
- SMTP 主机、端口、连接安全模式（STARTTLS、TLS 或受控明文）；
- SMTP 用户名和只写密码；
- 连接与发送超时；
- 测试收件地址和“发送测试邮件”；
- 最近一次测试时间、结果、稳定错误分类和配置版本；
- 全局“启用服务邮箱”；
- “注册必须验证邮箱”独立开关；
- “允许通过邮箱重置密码”独立开关。

### 10.2 开关行为

| 状态 | 注册验证码 | 忘记密码 | 页面行为 |
| --- | --- | --- | --- |
| 服务邮箱关闭 | 不可启用 | 不可启用 | 隐藏发码/忘记密码操作并说明管理员未启用 |
| 服务邮箱开启但测试未通过 | 不可启用 | 不可启用 | 显示配置待验证，只允许管理员测试 |
| 注册验证开启 | 注册前强制验证码 | 由密码重置开关决定 | 邮件故障时注册失败关闭，不绕过验证 |
| 密码重置开启 | 由注册验证开关决定 | Keycloak 发送重置链接 | 登录页显示“忘记密码” |
| 两项均关闭 | 不发注册验证码 | 不允许邮件找回 | 邮箱仍可作为登录名 |

两个业务开关互相独立，但都依赖全局服务邮箱已启用且测试通过。不能因为 SMTP 临时故障自动关闭“注册必须验证邮箱”，否则会形成安全降级；运行时应返回可恢复的“邮件服务暂不可用”状态并记录告警。

### 10.3 密码重置流程

密码重置继续由 Keycloak 完成，TermLink Server 不生成、不保存密码重置 Token：

```text
登录页 → 忘记密码 → 输入邮箱或用户名
  → 始终返回相同提示
  → Keycloak 向账号已绑定邮箱发送一次性重置链接
  → 完成密码更新
  → 撤销该账号现有浏览器会话；原生客户端按 Token 生命周期重新登录
```

- 开关启用时同步 Keycloak `resetPasswordAllowed=true`；关闭时同步为 `false`；
- 重置请求必须限速、防枚举，并使用统一成功响应；
- 链接使用公开 HTTPS 域名，不使用容器名、内网地址或请求头拼出的不可信 Host；
- 邮件模板使用 TermLink 品牌，并同时提供中文和英文；
- 管理员不能查看用户密码，也不能把临时密码通过审计日志或页面明文发送给用户。

### 10.4 配置发布与 Secret 处理

- 只有完成近期 Web MFA 的 SUPER_ADMIN 可以查看状态、修改配置或开启功能；
- SMTP 密码只写不读，页面只显示“已配置/未配置”，服务端不回传掩码伪值；
- Secret 使用现有密钥体系加密或外部 Secret 引用，不能写入普通配置 JSON、日志、审计 metadata 或前端持久化；
- 保存先形成草稿，只有测试邮件成功后才能原子发布并同步 Keycloak SMTP 配置；
- 同步失败时保留上一份可用配置和开关，不能产生 Server 与 Keycloak 一边成功、一边失败的半配置状态；
- 修改、测试、启停和回滚都写审计，但审计只记录操作者、配置版本、动作、结果和错误类别；
- 支持回滚到上一份已验证配置，并提供本机运维命令处理管理页面不可用的情况。

## 11. Google Authenticator 方案

### 11.1 标准与策略

使用 Keycloak 的标准 TOTP：

- RFC 6238；
- 30 秒周期；
- 6 位数字；
- 与 Google Authenticator、Microsoft Authenticator、1Password 等兼容；
- QR Code 和手动密钥只由 Keycloak 在绑定时短暂展示；
- 绑定必须先进行密码或现有 MFA 的 step-up 认证。

### 11.2 用户流程

```text
头像 → 登录与安全 → 绑定身份验证器
  → 近期认证
  → Keycloak CONFIGURE_TOTP 安全动作
  → 扫码并输入一次动态码
  → 生成恢复代码
  → 自动返回 /account/security
```

这不是旧的 Keycloak Account Console 跳转。用户从统一页面发起，并自动返回统一页面；只有处理密码和 TOTP Secret 的安全步骤由同域、同品牌的 Keycloak Required Action 页面承载。这样可避免 TermLink Server 接触认证 Secret。

需要为以下 Keycloak 页面补齐 TermLink 主题：

- TOTP 绑定；
- TOTP 登录；
- 更新密码；
- 恢复代码；
- Required Action 成功与失败。

### 11.3 登录规则

- MFA 只保护网页登录，不改变 Android 和 Windows/PC 客户端的登录流程；
- 普通用户可以选择绑定；一旦绑定，后续 Web 浏览器登录必须校验 TOTP；
- AUDITOR、ADMIN、SUPER_ADMIN 进入管理中心前必须已绑定并完成 MFA；
- 管理员角色授予后，如果尚未绑定，下一次进入管理中心先完成绑定；
- Web 高风险操作继续要求最近 10 分钟的真实 MFA，不因已有登录会话而放宽；
- 丢失验证器时使用一次性恢复代码或受审计的管理员恢复流程。

### 11.4 Web 专用 Flow 隔离

必须为 `termlink-web` 单独配置 Web Browser Authentication Flow，并通过客户端级 `authenticationFlowBindingOverrides` 绑定：

- `termlink-web` 使用带 Conditional OTP/TOTP 的专用 Browser Flow；
- `termlink-android` 和 `termlink-windows` 不绑定该 Browser Flow；
- Android/Windows 当前 Direct Grant 或各自客户端流程不要求 OTP；
- 不设置 realm-wide 全局 OTP，不修改原生客户端的 Direct Grant Flow；
- 管理员未绑定时，由 Web 管理入口发起浏览器内的应用初始化动作，不给账号挂会阻塞原生客户端的长期全局 Required Action。

这意味着本轮 TOTP 是“TermLink Web MFA”，不是覆盖整个账号全部客户端的全局 MFA，产品文案必须如实说明。验收必须证明绑定 TOTP 后 Android 和 Windows 仍可按现有方式重新登录，同时 Web 登录和管理中心确实要求 TOTP。

## 12. 功能显示与运行能力

用户要求“简约易用”的关键是只展示当前真的可用的功能。新增统一 Runtime Capability 模型：

| 能力 | 页面行为 |
| --- | --- |
| 支付渠道未配置 | 不展示可提交的支付方式，显示“暂未开放在线支付” |
| 账号注销处理器未启用 | 不显示注销按钮，显示当前未开放及原因 |
| 数据导出不可用 | 不创建无法领取的任务 |
| AppShip 分发不可用 | 不展示未验证下载，显示检查时间与恢复说明 |
| 管理权限不足 | 不输出管理菜单与入口 URL |
| 服务邮箱关闭或未验证 | 不展示可提交的发码、找回密码操作，管理端显示配置状态 |
| 注册邮箱验证已开启但 SMTP 故障 | 暂停注册并给出可恢复错误，不降级为免验证注册 |
| Web TOTP Flow 未正确绑定 | 不开放自助绑定和管理入口，原生客户端登录不受影响 |

能力必须由 Server 生成，模板和 API 共用同一权威值。

## 14. 验收标准

### 14.1 首页与登录

- 首页只出现一个登录入口；
- 已登录用户访问首页直接进入用户仪表盘；
- 登录成功不经过中转介绍页；
- 同一输入框可使用用户名或邮箱登录，失败响应不泄露账号是否存在；
- 首页在手机和桌面首屏均无重复 CTA。

### 14.2 注册与账号标识

- 注册页不存在姓、名字段，只包含用户名、昵称、邮箱、策略要求的验证码/邀请码和密码；
- 用户名创建后不能通过用户页、管理页或普通 API 修改；
- 昵称可重复、可修改且通过 `nickname` claim 正确返显；
- 修改昵称或验证后的邮箱不会改变 `users.id`；
- 用户 ID 可在个人设置中只读查看，所有业务外键仍关联该 UUID；
- 邮箱验证开启时，未通过或已过期的验证码不能创建账号、消耗邀请码或标记邮箱已验证；
- 重发、并发提交、结果不确定和恢复任务不会重复创建账号或重复兑换邀请。

### 14.3 用户中心

- USER 的 HTML 响应中不存在管理菜单和管理 URL；
- 默认显示用户自己的设备、PC、会话和权益摘要；
- 头像菜单可以完成个人设置、安全和退出；
- 所有旧用户功能在统一页面可达；
- 窄窗口无关键内容被滚动条或侧栏遮挡。

### 14.4 管理中心

- 只有 AUDITOR、ADMIN、SUPER_ADMIN 能进入；
- 自定义入口启用后，`/admin` 与旧入口统一返回 404；
- 访问错误入口不会触发登录或泄露新入口；
- 直接访问正确入口可完成登录并返回管理中心；
- 普通用户即使知道入口仍不能打开管理页面；
- 可通过本机离线命令恢复入口；
- 路由变更不出现在普通日志和公开页面。

### 14.5 服务邮箱和密码重置

- 未配置 SMTP 时，注册发码和忘记密码操作都不伪装成可用；
- 只有近期完成 Web MFA 的 SUPER_ADMIN 能保存、测试、启停或回滚服务邮箱；
- 测试邮件成功后才能启用依赖功能；
- 注册验证与密码重置开关可以独立启停；
- 注册验证开启而 SMTP 故障时系统拒绝免验证注册；
- 忘记密码关闭时登录页不显示入口，Keycloak 对应能力也关闭；
- 忘记密码开启时可通过邮箱或用户名请求邮件，响应不泄露账号存在性；
- SMTP 密码、验证码和重置 Token 不进入 HTML、API 响应、普通数据库列、日志或审计；
- Keycloak 同步失败时继续使用上一份已验证配置，不出现半发布状态。

### 14.6 Google Authenticator

- Google Authenticator 扫码后可以使用 6 位 TOTP 完成绑定；
- 绑定账号下一次 Web 登录必须完成 TOTP；
- 绑定后 Android 和 Windows/PC 仍可按现有流程登录，不显示或要求 OTP；
- 管理角色未完成 MFA 时无法进入管理中心；
- TOTP Secret 不进入 TermLink 数据库、日志、审计或前端持久存储；
- 恢复代码可用且只能显示一次；
- 丢失验证器存在受控恢复路径；
- realm-wide Flow 和原生客户端 Direct Grant 未被 Web MFA 配置修改。

## 15. 不建议采用的实现

- 仅把 `/admin` 改成前端隐藏链接，但服务端仍允许旧地址；
- 把完整管理 URL 当成唯一认证凭据；
- 把 Web TOTP 设置成 realm-wide OTP，导致 Android/Windows 登录被影响；
- 在 TermLink Server 自己生成或保存 TOTP Seed；
- 继续在注册页采集姓、名，或把昵称伪装写入姓、名；
- 使用用户名、邮箱或昵称作为业务表主键或外键；
- SMTP 未测试成功就显示注册发码或忘记密码可用；
- 邮件故障时自动绕过已开启的注册邮箱验证；
- 在普通配置、日志或审计中保存 SMTP 密码、邮箱验证码或重置 Token；
- 让注册验证码与密码重置 Token 共用数据模型或校验用途；
- 通过 iframe 嵌入完整 Keycloak Account Console；
- 为统一页面引入重量级 SPA 并复制现有权限判断；
- 用前端菜单隐藏代替 API 和服务端模板授权；
- 管理入口变更后直接删除恢复手段。

## 16. 实施结论

这些需求可以整合为一套一致的产品：公开首页只负责了解和进入产品；登录后直接进入统一用户仪表盘；管理能力从头像菜单切换且由安全入口保护；注册只收集必要资料；用户名和邮箱可登录，昵称用于展示，不可变用户 ID 承担所有内部关联；所有个人资料和身份安全在统一用户中心发起。

实现顺序不能只按页面视觉推进。应先完成运行能力真实性、注册字段和登录落点，再合并用户中心，然后实施动态管理入口，最后接通经过测试的服务邮箱和 Web 专用 MFA。邮件相关开关必须以实际投递能力为前提，Web MFA 必须通过客户端级 Flow 隔离，不能改变 Android/Windows 的登录行为。
